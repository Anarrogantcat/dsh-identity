# 方案：双通道可切换（官方 QQ ⇄ NapCat/OneBot），只出方案不动手

> 状态：**待批准**。本文只描述设计，不改任何配置/代码。
> 结论先行：**主线转 NapCat（OneBot），官方通道降级为备胎**；单活开关切换；不硬依赖腾讯插件；群级数据可共用/可一次性迁移，成员画像需人工映射。
> 前提事实（已核实）：NapCat 账号 **100000001（小号）** 在 `D:\AI\QQBOT\NapCat`，用 `websocketClients` 主动连 `ws://localhost:2536/OneBotv11` 给 Yunzai；
> DSH 侧 `dsh-onebot-qq@0.9.6` 已装未挂载；`dsh-qqbot-refine` 现挂官方 `im-qqbot`（账号 **100000000**）。
>
> ✅ 已确认：两条通道用**不同 QQ 号**（官方 100000000 / OneBot 100000001 小号）。
> ✅ 按最新要求：**单活（不共存）+ 不强依赖腾讯官方插件**，开关切换，切换需重启。

## 1. 目标（按最新要求：单活 + 不硬依赖）

两条通道**互斥启用**，同一时刻只挂一条：
**官方 QQ（im-qqbot）** ⇄ **OneBot/NapCat（小号 100000001）**，由一个开关决定，切换 = 改一个值 + 重启（约 30 秒）。

两条硬性要求：
1. **不强依赖腾讯官方插件**：`dsh-qqbot-refine` 在腾讯插件不存在 / 被卸载时也要能正常加载、跑 onebot 通道，绝不 import 就炸。
2. **不共存**：同一时刻只挂一条通道，避免回声、抢话、token 双倍、两套状态机互相干扰。

## 2. 开关怎么定义

```yaml
# settings.json → transport
transport:
  mode: tencent        # tencent | onebot（没有 auto：不共存，必须明确选一个）
  switchRequiresRestart: true
```

### 切换动作（面板「通道」页一键）

```
1. 备份 cordis.patch.yml
2. 注释掉当前通道块 / 展开目标通道块（保留对方配置，便于随时切回）
3. 写入 transport.mode
4. 提示：重启 DSH 生效（约 30 秒）
```

> 为什么必须重启：通道插件在启动时决定是否监听 WS / 是否建 agent，运行期热插拔会把两个状态机搅在一起。
> 切换过程**不删任何配置**，两边白名单、密钥、token 都留在文件里，回滚 = 再点一次。

## 2.1 依赖解耦清单（"不强依赖"落在哪几行）

| 位置 | 现状 | 改成 |
|---|---|---|
| `lib/diag.js` `loadQQBot()` | 用 createRequire 解析 `@tencent-connect/dsh-qqbot`，失败会抛 | 解析失败 → 返回 `{ error: 'not-installed' }`，调用方跳过，不抛 |
| `lib/diag.js` `installHooks()` | 直接包 `QQBot.prototype` | 移到 `transport/tencent.js`，仅 mode=tencent 时调用 |
| `lib/index.js` 启动流程 | 无条件 `loadQQBot()` | 先读 `transport.mode`，只加载对应 transport |
| `lib/api.js` `readCredentials()` | 读 profile 的 `cordis.patch.yml` 取 appId/appSecret | 仅 tencent 通道用；onebot 下返回 null，且所有调用点容忍 null |
| `lib/gate.js` `appId` / `sessionIdFor` | 由 appId 推导会话 id | 走 `transport.sessionIdFor()`（tencent: qqbot:appId:…；onebot: onebot:group:gid） |
| `lib/usage.js` 真实用量 | 用 appId 推 DSH 会话 id | onebot 下退回「闸门计数」，并标注「该通道无用量映射」 |
| `lib/toolgate.js` | 包 `tools` 服务（与通道无关） | 不用改 |
| 看图 / 媒体 | 依赖腾讯插件下载目录 `~/.dsh-qqbot/media` | onebot 用自己的媒体目录；我们的下载逻辑保留 |

结论：**没有 npm 依赖**（package.json 本来就没依赖它），要拆的是**代码级耦合**，集中在 diag / index / api / gate 四处。

## 3. 适配层设计（P1 的核心）

```
lib/transport/
  index.js     mode 解析 + 只有 active 通道装钩子；暴露 status()
  tencent.js   把现 diag.installHooks / gate 出站包装搬进来
  onebot.js    包 dsh-onebot-qq 的入站/出站（见 §4 的接入方式）
  types.md     接口契约
```

接口契约（两种实现必须一致）：

| 方法 | 说明 |
|---|---|
| `installHooks(handler)` | 返回是否成功；idempotent |
| `sendText(target, text)` / `sendImage(target, {url|localPath})` / `sendMarkdown` | 出站三件套 |
| `replyTargetOf(raw)` | 回复目标（群/私聊 + id） |
| `sessionIdFor(scope, peer)` | 会话 id 推导（persona/记忆映射用） |
| `describe()` | 面板诊断：连接状态、账号、延迟、最近事件 |
| `capabilities()` | 能力位：见 §5 矩阵 |

**不动的东西**：隐私脱敏、频率闸、学习、心情、知识库、人设、人类化输出、工具闸 —— 全在 gate 之上，一行不改。

## 4. 与 dsh-onebot-qq 的接入方式（三条路，按优先级）

1. **上游加钩子（最优，利于开源）**：给它提 `beforeInbound / beforeSend` 扩展点（它现在没有公共 hook API），我们订阅。
2. **包它导出的类**：`ChatBridge` / `inbound.js` / `outbound.js` 都是 ESM 导出，可像我们现在包 `QQBot.prototype` 一样包它的方法（实现快，但随它版本变）。
3. **外挂旁路**：我们直接当第二个 OneBot 客户端连 NapCat，自己收发，不用它的通道（重复造轮子，但完全可控）。

建议：**先 2 后 1**（先跑通，再提 PR 变成正式扩展点）。

## 5. 能力矩阵（切过去哪些能用、哪些降级）

| 能力 | 官方 QQ | OneBot/NapCat | 切换后处理 |
|---|---|---|---|
| 群全量消息 | 需在机器人资料页手动开 | 原生 | 无需处理 |
| 群名片 | 拿不到（只有 QQ 昵称） | `sender.card` | 自动变好 |
| 成员信息 | 30 QPM | 无限制 | 自动变好 |
| 主动消息额度 | 有 | 无（本地发送） | 闸门照旧控频 |
| 图片/语音 | 签名链接，需补丁 | 本地 file/url | 我们的下载逻辑保留 SSRF 校验 |
| 撤回 / 戳一戳 / 合并转发 | 无 | 有 | 可选接（默认关） |
| Markdown / 卡片 | 受限 | t2i 卡片 | 注意与我们 `plainText` 去重 |
| 分段发送 | 我们自己做 | **它自带**（按句切） | 切换时关掉我们的 `splitBubbles`，避免双切 |
| 语音 TTS | 我们接外部服务 | 它自带 STT（入站） | 出站仍用我们的 |
| 工具 | 我们包 `tools` | 它自带 `qq_*` 工具 | 工具闸 allowlist 显式列出 |

## 6. 数据身份问题（最容易踩的坑）

记忆/画像/学习/心情/收集表情都按 `peerKey = g_<sha12(peer)>` 存，**而两条通道的 peer id 根本不同**：

- 官方：群 openid（如 `6EC25148…`）
- OneBot：群号（如 `123456789`）

直接切 → 记忆、画像、学到的规矩、"这个群爱不爱接话"的统计 **全部看起来是空的**。

> 现在两条通道是**不同号、不同群**，所以天然是两套独立数据，这是**正确**的（不同群的记忆本来就不该混）。
> 只有「把主群搬到小号」时，才需要下面的别名表。

三个处理方式（建议 3）：

| 方式 | 做法 | 代价 |
|---|---|---|
| 1 各存各的 | 切成两套孤岛 | 体验断层 |
| 2 一次性迁移 | 把旧 `g_6ad5…` 目录改名成新的 | 不可逆、要备份 |
| **3 别名表（推荐）** | 新增 `peerAlias.json`：`{ "g_6ad5…": "g_<新>" }`，读的时候走别名 | 小改动，可回滚 |

## 9. 风险与回滚

- 封号：OneBot 非官方协议 → 小号 + 闸门控频；官方通道保留随时切回
- 双通道抢话：只在「同群双机器人」形态下存在 → 用「只响应 @ 自己/自己的别名」+ 丢弃机器人消息两条规则

- 插件升级覆盖：我们对 third-party 的补丁（图片下载 DNS 回落、可能的类包装）要写进文档，升级后重打

## 10. onebot 通道下 refine 各功能的落地方式

| refine 功能 | 在 onebot 下怎么做 |
|---|---|
| 入站闸门（频率/隐私/白名单） | 包它 inbound 的出口（或它的 beforeInbound 钩子） |

| 学习（规矩/倍率） | 不用改 |

## 12. 跨通道共用数据（记忆/画像/规矩/知识/心情）

### 结论

**群级数据能共用，成员级画像做不到自动共用**——因为两条通道拿到的人 id 根本不同（官方是 openid，OneBot 是 QQ 号，无法互推）。

### 12.1 共用靠「规范身份」（canonical peer）

现在所有数据都按 `peerKey = g_<sha12(peerId)>` 存。新增一层映射，把两条通道的 id 指到同一个规范键：

```yaml
identity:
  mode: shared            # shared（同一物理群，共用一份）| isolated（各存各的）
  links:
    - label: 主群
      tencent: "6EC25148B7DCD81CDD999EF9D6811D5A"
      onebot:  "123456789"
```

运行时：`resolvePeerKey(transport, scope, peer)` 先查 links，命中就用**规范键**，落库时统一写入同一个 `g_<canonical>`。

这样切换通道后：
- 记忆、学到的规矩、接话倍率、收集的表情、知识库 → **无缝接上**
- 心情本来就是单实例（本地引擎/LLM 评估），天然共用
- 对话历史（DSH 会话）**不共用**：不同通道 = 不同 DSH 会话（这点要接受）

### 12.2 能共用 vs 不能

| 数据 | 能否共用 | 说明 |
|---|---|---|
| 长期记忆（每群） | ✅ 群级映射即可 | 文本内容与通道无关 |
| 学到的规矩 / 接话倍率 | ✅ | 按群统计 |
| 收集的表情 / 表情库 | ✅ | 图库本来就是全局的 |
| 知识库 | ✅ | `g_xxx.md` 用规范键命名即可 |
| 心情（本地/LLM） | ✅ 天然共用 | 单实例 |
| 成员画像 | ⚠️ **不能自动** | 官方 openid ↔ QQ 号无法互推；只能人工映射或让它在 onebot 侧重新攒 |
| 真实 token 用量（元） | ⚠️ 退化为计数器 | 会话 id 与 DSH projcache 映射不稳 |

成员画像的补救：`identity.people` 里手工写 `{ openid: "...", qq: 123456 }`，只对少数关键人（Owner、管理）做映射，其余人各自重建。

### 12.3 老数据怎么办（三选一）

| 方式 | 做法 | 评价 |
|---|---|---|
| **A 直接映射（推荐）** | 加 links 后，旧数据保持原名，读取时通过 links 反查 | 零迁移、可回滚，代码多几行 |
| B 一次性重命名 | 把 `g_6ad5…` 改成 `g_<群号>` | 干净，但不可逆（要备份） |
| C 各存各的 | 不映射 | 切过去记忆像清空过 |

  记忆 17 条 · 规矩 2 条 · 倍率 ×1.2 · 收集图 8 张 · 知识 7 段

- 共用后两边的"群名/氛围"其实是同一个群，所以风险可控；**不同群请用 isolated**

## 13. 主线转向 NapCat（按最新判断调整优先级）

> 前提：后续大概率**只用 NapCat（OneBot）**，官方通道退居"兜底/合规备胎"。

### 13.1 优先级重排

| 阶段 | 原计划 | 调整后 |
|---|---|---|
| S1 解耦 + 适配层 | 半天 | **不变**（先破依赖，行为不变，53 测试全绿） |
| S2 OneBot 实现 | 1 天 | **升为主线，1.5 天**（一次做到位：入站/出站/图片/分段去重/工具 allowlist） |
| S3 面板「通道」 | 半天 | 半天（但默认值改成 onebot） |
| S4 数据 | 半天 | **按 13.3 选一条路**（迁移 / 重新开始） |
| S5 文档 | 2 小时 | 2 小时（README 改成「优先 OneBot，官方可选」） |
| 腾讯通道 | — | **只做回归验证，不再加新功能** |

### 13.2 NapCat 带来、我们可以直接吃的红利

| 能力 | 对 refine 的价值 |
|---|---|
| `sender.card`（群名片） | 叫对人名，终结「剑缘随风」问题；画像卡片直接用群名片 |
| 群全量消息 | 不用再让管理员去开「获取全部消息」 |
| `get_group_member_list` 无限流 | 画像/群管识别可实时刷新，不用 30QPM 事件缓存 |
| 撤回 / 戳一戳 / 合并转发 | 可以做「被撤回的消息不回答」「被戳一下有反应」「转发内容能读」 |
| 本地 file/url | 表情收集不再受签名过期影响（**收集率会明显上升**） |
| 原生按句分段 | 我们的 `splitBubbles` 在 onebot 下应关闭，避免双切 |

### 13.3 数据怎么走（取决于一件事）

**关键问题：Nap 小号会不会进现在的主群？**

| 情况 | 处理 |
|---|---|
| **会进主群**（同一批群友） | 做**一次性迁移**：把官方号时期的主群数据（记忆 17 条 / 规矩 / 倍率 / 收集图）按 `tencent-openid → onebot-group` 映射改名，重命名前自动备份；成员画像按人工映射关键人，其余重建 |
| **进新群/新一批人** | **不迁移**，直接在新群重新开始（旧数据留在磁盘，随时可查） |

两种都**不需要**长期维护别名表——因为不共存，只有一次切换。

### 13.4 官方通道的收尾（降级为备胎）

- `im-qqbot` 配置保留但默认不启用（`transport.mode: onebot`）
- 我们在 `node_modules/@tencent-connect/dsh-qqbot` 打的补丁（图片下载 DNS 回落）**只在官方通道启用时才有意义** → 文档标为 legacy，不写进 README 的安装步骤
- 官方号可继续留着当"合规演示"/应急：切回去只需改一个值 + 重启

### 13.5 在 NapCat 主线下建议做的三个新产品特性

1. **群名片同步**：画像卡片用群名片；被叫名字的识别同时匹配群名片（不用每次叫全名）
2. **撤回不答**：被撤回的消息入队后丢弃（避免回答"已经不存在的问题"）
3. **表情收集升级**：Nap 给本地文件，收集直接落地，收满可自动打情绪标签（省一次模型调用：先按尺寸/尺寸比筛，再由模型标）

### 13.6 风险（主线转向后）

- NapCat 跟随 QQ 版本：**大版本更新可能打断** → 保底方案就是官方通道，别删配置
- 小号封号：控制频率（闸门已有）、别做敏感操作
- 「只用 nap」后，官方的审核/合规优势没了 → 如果未来要对外/商用，仍建议保留官方号

## 14. 封号风险：谁能管、管到哪（不能全甩给 NapCat）

### 14.1 先说结论

**NapCat 抗不了封号。** 它只是 OneBot 协议的实现（把 QQ 客户端的行为翻译成 API），
协议本身是非官方的 —— 风控看到的是「这个 QQ 号在异常地高频收发」，而不是「用了 NapCat」。

所以责任必须分三层：

| 层 | 能做的 | 做不到的 |
|---|---|---|
| **NapCat** | 连接稳定、重连退避、上传/下载限速（`timeout.uploadSpeedKBps / downloadSpeedKBps`）、超时控制 | 替你抗风控、规避检测 |
| **dsh-qqbot-refine（我们）** | **发言频率闸**（每小时/每天/每群/每人）、间隔、免打扰、随机跳过、不主动私聊陌生人、脱敏不外泄、内容不敏感 | 决定腾讯的风控策略 |
| **Yunzai** | 它自己插件的推送频率（B站动态等大量推送是**风险源**） | — |

一句话：**NapCat 负责"送得出去"，我们负责"别送太多、别送错东西"。**

### 14.2 风险最高的几个行为（按危险度排序）

1. **短时间内大量群发/主动推送**（Yunzai 的 B 站动态推送如果一次推几十条，是最像营销号的画像）
2. **连续 @ 大量成员 / 群发私聊**
3. **同一句话重复刷屏**（我们的 dedupe/selfGap 已经在挡）
4. **敏感内容触发举报**（图片、政治、擦边 —— 我们的隐私闸只管外泄，不管内容合规）
5. **新号马上高频使用**（小号刚上线就活跃，画像最可疑）

### 14.3 建议加「安全模式」预设（一键）

```yaml
transport:
  mode: onebot
safety:
  profile: safe          # safe | normal | off
```

| 参数 | safe 值 | 说明 |
|---|---|---|
| 每群每小时发言 | ≤ 30 | 闲聊也够 |
| 每群每天 | ≤ 150 | |
| 单条最小间隔 | ≥ 8 秒 | 人打字没那么快 |
| 主动搭话 | **关** | 最像机器人的行为 |
| 私聊陌生人 | **禁止** | 只在白名单私聊 |
| 随机跳过 | 20% | 少一点"有问必答"的机械感 |
| 长消息分段 | ≤ 2 条 | 少刷屏 |
| 图片/文件 | 单群每日 ≤ 10 | 少触发媒体风控 |

「safe」= 更像人、更少触发；「normal」= 现在的默认。

### 14.4 我们该加的「损伤控制」

被风控时 NapCat 会返回错误（发送失败、需要验证、被踢出群）。现在这些错误只会打日志。
建议加：

- **发送失败熔断**：连续 3 次发送失败 → 进入保护模式 30 分钟（只读不回），并推一条通知给 Owner（面板 + 私聊）
- **被踢/被禁言检测**：入站事件里出现"移出群/禁言"→ 自动从该群白名单摘除并记录
- **启动冷却**：DSH 重启后 5 分钟内不主动发起任何消息（避免重启风暴被判定异常）
- **审计**：`audit.js` 记 `send.fail` / `safety.trip`，面板「用量」页显示

### 14.5 NapCat 侧建议调的参数

| 参数 | 建议 | 理由 |
|---|---|---|
| `timeout.uploadSpeedKBps` | 保持 256 或更低 | 上传过猛容易被盯 |
| `timeout.downloadSpeedKBps` | 保持 256 | 同上 |
| `timeout.maxTimeout` | 保持 1800000 | 大文件别断 |
| `websocketClients.debug` | 试跑期 true，稳定后关 | 日志量 |
| 多账号 | 如果以后加号，**一个 NapCat 实例一个号** | 交叉污染 |

### 14.7 存量号的风险模型（小号已稳定跑几个月）

这是**好消息**，但要改一下风险判断：

| 维度 | 新号 | 存量号（现状） |
|---|---|---|
| 注册时长 / 历史行为 | 高风险（新号高频最可疑） | 低（有正常使用历史，权重高） |
| 被举报敏感度 | 高 | 中（群友熟悉这个号） |
| 被封代价 | 低 | **高**（群、好友、历史都在这个号上） |

**风险的重心从「号太新」变成「行为模式突变」。**
这个号这几个月的行为是「低频、结构化推送」（Yunzai 的 B 站动态），
而我们要给它加的是「高频闲聊 + 主动说话 + 频繁看图」——**对新行为的容忍度是未知的**。

所以策略要更保守，不是更激进：

1. **先只放 1–2 个群**试跑一周，不一次性铺开
2. **主动搭话继续关**（`safety.profile: normal` 但 `proactive.enabled: false`）——主动消息是最高风险行为
3. **图片/文件限频**（单群每天 ≤ 10）
4. **不做任何群发、批量 @、自动加群**
5. 观察期一旦出现「发送失败 / 需要验证 / 消息被折叠 / 被禁言」，立即降级到只读

### 14.8 风控信号怎么采集（现有条件有限，得补）

实地查过：

| 来源 | 现状 |
|---|---|
| NapCat 日志 | `D:\AI\QQBOT\NapCat\logs` **是空的**——它只打控制台（PowerShell 窗口里那些行） |
| Yunzai 日志 | `logs\command.*.log` / `logs\error.log` 有，且**同一个号**，能反映发送异常 |

建议：

1. **NapCat 输出落盘**：用它自带的日志文件开关，或把 PowerShell 输出重定向到 `logs\napcat-YYYYMMDD.log`
2. **我们的熔断**（已在 14.4）：连续 3 次发送失败 → 保护模式 30 分钟
3. **关键词扫描**（可选）：读 NapCat/Yunzai 日志尾部，命中 `风控|限制|需要验证|禁言|踢出|消息被拒|发送失败` → 面板标红 + 通知 Owner
4. 面板「通道」页显示健康度：🟢 正常 / 🟡 偶发失败 / 🔴 触发保护模式

### 14.6 工作量

安全模式预设 + 失败熔断 + 群内禁用检测：**+0.5 天**（放进 S2 之后、S3 之前）。


## 16. 拟人化参数组（S2 一起做，已按你的意见去掉夜间下线）

> 已确认：**不做夜间下线**（晚上也要在）。其余三条照做。

现有基础：`typingDelayMs = 250ms + 字数 × 25ms`，±20% 抖动，封顶 2.5s；长回复按句拆条。

### 16.1 按内容分档的回复延迟

| 内容长度 | 延迟范围 | 说明 |
|---|---|---|
| ≤ 20 字（短句） | 1.0 – 2.0 秒 | 随口应一声 |
| 21 – 60 字 | 2.0 – 3.5 秒 | 正常说话 |
| > 60 字（要给分析） | 3.0 – 6.0 秒 | 像在组织语言 |
| 抖动 | ±25% | 避免整齐划一 |
| 封顶 | 8 秒 | 别让人以为卡住了 |

配置：`humanize.delayMode: byLength`（新）｜`humanize.maxDelayMs: 8000`

### 16.2 被 @ 也不秒回

被 @ / 被叫小名时，**最少等 1.5 秒**再发（现在是立刻发，太像自动应答）。

配置：`humanize.mentionMinDelayMs: 1500`

### 16.3 偶尔连发两条（想到补一句）

- 概率：**8%**
- 条件：回复长度 ≥ 25 字且能拆出 ≥2 句
- 行为：先发主句，隔 0.4 – 1.2 秒补第二句
- 上限：每条回复最多补 1 次（别变成刷屏）

配置：`humanize.occasionalSecond: 8`（百分比，0 = 关）

### 16.4 明确不做

- ❌ 夜间下线（按你的意见取消）
- ❌ 故意打错字再纠正（容易看起来像 bug，不做）
- ❌ 伪造"正在输入"（协议层没有这个状态，做不了）


## 17. 单群部署基线（按"主要就一个群、token 有开销"定）

### 17.1 安全与频率默认值（单群版）

| 参数 | 值 | 理由 |
|---|---|---|
| 白名单群 | **1 个** | 单群 |
| 每群每小时发言 | 30 | 单群容易聊嗨，这条是关键闸 |
| 每群每天 | 150 | |
| 单条最小间隔 | 8 秒 | |
| 每条消息冷却 | 90 秒（`cooldownGroupSec`） | 非点名时不至于刷屏 |
| 主动搭话 | **关** | 单群主动开口最像机器人 |
| 随机跳过 | 10% | 别"有问必答" |
| 图片/文件 | 单群每日 ≤ 10 | |

### 17.2 花费闸（单群最该加的）

现在只有「记录金额」，**没有硬上限**。建议加：

```yaml
usage:
  dailyYuanHardLimit: 2.0     # 每天最多花 2 元
  onExceed: degrade           # degrade（降级到 0 token 回复）| mute（静默到明天）
```

- **degrade**：超预算后只用命令/模板回复（`#帮助` 这类照旧），闲聊只回一句"今天本鱼吃撑了，明天再聊"
- 面板「用量」页显示：今日金额 / 硬上限 / 剩余
- 与现有 `groupDailyYuan`（软预算，只告警）区分

### 17.3 数据（单群 = 迁移最简单）

- 只有一个群 → **别名表不必长期维护**，一次性改名即可（备份后把 `g_6ad5…` 改成 `g_<群号>`）
- 若这个群就是官方号现在在的那个群 → 记忆 17 条、规矩、倍率、收集图都能带过来
- 若换新群 → 直接从零开始，旧数据留档

### 17.4 成本体感（按现在的量估算）

| 项 | 估算 |
|---|---|
| 正常闲聊（每天 100 条群消息、她回 20 条） | 约 ¥0.1–0.3/天 |
| 看图（每张约 1.5k–3k tokens） | 约 ¥0.01–0.02/张，限 10 张/天 |
| 模型评估心情（每日上限 20000 tokens） | ≈ ¥0.04/天 |
| **合计** | **≈ ¥0.2–0.5/天，¥6–15/月** |

（按默认单价：输入未命中 ¥2/M、命中 ¥0.2/M、输出 ¥3/M）

### 17.5 单群带来的额外好处

- 画像更准（人数少、样本集中）
- 学到的规矩不会串群
- 心情/知识库只需要维护一份
- 面板"每群明细"退化成一行，看着更清爽


## 15. 目标补充：单活不是终点

> 单活只是手段；真正的目标是：**在只有一个群、又有 token 开销的前提下，稳定、像人、不封号、花费可控**。
> 因此优先级是：解耦（S1）→ 通道跑通（S2）→ 花费闸（S2.5）→ 数据（S4）→ 面板与文档（S3/S5）。
