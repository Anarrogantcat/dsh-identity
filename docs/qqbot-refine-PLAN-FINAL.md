## 2. 目标与原则

1. **NapCat 为主线**（后续基本只用它），官方通道降级为备胎
2. **单活切换**：同一时刻只挂一条通道；切换 = 改配置 + 重启（约 30 秒），可一键回滚
3. **不硬依赖腾讯插件**：它不存在时插件照常加载并跑 OneBot
4. **能力由模式决定**：官方拿不到的能力（群名片/撤回/戳/转发/表情/引用/视频/STT）在官方模式**不注册**、面板置灰并写明原因
5. **单群优先**：默认值按单群调（频率、花费、安全）
6. **钱要有闸**：花费硬闸默认关闭，但**一个开关就能打开**，超限降级或静默

### 4.2.1 拓扑分支（按实测与你的实际情况二选一）

**拓扑 A（实测如此）**：NapCat 作为客户端 → 连 Yunzai 的 OneBot WS 服务端（2536）
- 加 DSH 的办法：在 NapCat 的 `websocketClients` **追加一个独立客户端** → `ws://127.0.0.1:8643`（DSH 反向 WS 服务端）
- **不共用连接**：NapCat 的每个 `websocketClients` 条目是一条独立长连接，各自推一份完整事件流，各自断线重连、各自 token
- 不动 Yunzai 任何配置

> **共用的是什么？** 只共用「同一个 NapCat 进程 + 同一个 QQ 号（100000001）」这个事件源。
> 连接本身**不共用**——把两条框架塞进同一条 WS 是不可能的（一条 OneBot 连接只对应一个服务端）。

> **分工（已确认）**：Yunzai **不参与对话**，只做 **B 站动态推送 + 链接识别**；DSH 接管聊天/记忆/心情/群管。
> 所以"双机器人抢话"不存在，不需要分流规则。

### 4.2.2 与 Yunzai 的功能边界（避免重复动作）

| 能力 | 归谁 | 说明 |
|---|---|---|
| B 站动态推送 | **Yunzai** | DSH 侧 `bili.pushEnabled` 保持 **false**（现状） |
| B 站链接识别/解析 | **二选一** | 两边都有；建议 **Yunzai 保留**（它本来就是干这个的），DSH 侧 `bili.parseEnabled` 设 **false**，避免同一链接发两张卡 |
| 聊天 / 记忆 / 心情 / 画像 / 学习 / 知识库 | **DSH** | Yunzai 不参与 |
| 群管命令（禁言/撤回等） | **DSH** | Yunzai 不做 |
| 自己号发的消息（推送） | 两边都忽略 | NapCat `reportSelfMessage:false`（现状），不会把推送当入站事件；DSH 侧 `ignoreSelf` 仍按 P0 实现做兜底 |

**拓扑 B（若你实际是"NapCat 当服务端、Yunzai 连它"）**
- 需要 NapCat 开 `websocketServers`（默认 3001），DSH 用**正向 WS 客户端**连过去
- 同时 Yunzai 的 OneBot 地址要指向 NapCat 的 WS 端口

> 两种拓扑在方案里的差别只有"加客户端" vs "开服务端"，Adapter/能力位/闸门全都不受影响。

### 4.5 连接状态与健康度（有，分三层）

#### 4.5.1 现在就能看到什么（官方通道）

面板 `state` API 里已有：

| 字段 | 含义 |
|---|---|
| `diag.patch.inbound/outbound` | 入站/出站钩子是否挂上 |
| `diag.sdkVersion` / `sdkPath` | 通道插件版本与路径 |
| `diag.counts` | 入站/拦截/出站/脱敏/标记次数 |
| `botSeen` | 有没有收到过消息（bot 是否真的在线） |
| `toolGate.installed / blocked` | 工具闸是否生效 |

**缺口**：没有"当前是否连着"、没有"最近一次事件时间"、没有"重连次数/延迟"。

#### 4.5.2 OneBot 通道能补什么

dsh-onebot 自带连接层（`OneBotConnection`：重连退避、心跳、鉴权），并暴露：

| 来源 | 能给 |
|---|---|
| 连接对象状态 | 已连接 / 重连中 / 已断开 + 重连次数 |
| `get_login_info` | 当前账号 QQ 与昵称 |
| `get_status` | 是否在线、good |
| 事件时间戳 | 最近一次收到事件的时间（判断"卡住了没有"） |
| 发送结果 | 成功/失败计数、失败原因（风控信号） |

#### 4.5.3 面板要显示的（「通道」页）

```
当前通道：OneBot（100000001 · 已连接）
  ws://127.0.0.1:3001    延迟 12ms    最近事件 8 秒前
  重连 0 次 · 心跳正常 · 今日发 24 条 / 失败 0 条
  健康度：🟢 正常

另一条：官方 QQ（100000000）· 未启用
```

#### 4.5.4 健康度判定规则

| 状态 | 条件 | 面板 | 动作 |
|---|---|---|---|
| 🟢 正常 | 已连接 + 最近 10 分钟有事件或无活动但心跳 ok | 绿 | — |
| 🟡 可疑 | 连续 1–2 次发送失败，或 30 分钟无事件且有心跳 | 黄 | 记录 + 提示 |
| 🔴 异常 | 连接断开 / 连续 3 次发送失败 / 被踢 / 需验证 | 红 | **保护模式 30 分钟** + 通知 Owner |

#### 4.5.5 接口（面板用）

```js
// transport.describe()
{
  mode: 'onebot',
  connected: true,
  account: { uin: 100000001, nickname: '...' },
  endpoint: 'ws://127.0.0.1:3001',
  latencyMs: 12,
  lastEventAt: 1792950000000,
  reconnects: 0,
  heartOk: true,
  sentToday: 24, failedToday: 0,
  health: 'ok' | 'warn' | 'bad',
  lastError: ''
}
```

> 官方通道同结构：`connected` 由钩子是否挂载 + 最近事件推断，`account` 取 appId。

## 12. 插件侧方案：名册（群列表 / 好友列表 / 群成员）

> 这是**插件内**的能力，不是改 NapCat 配置。它依赖 OneBot API，所以挂在通道层之上。

### 16.1 为什么需要

| 现在的痛点 | 名册能解决 |
|---|---|
| 白名单要手抄群号 | 从 `get_group_list` 里选群 → 一键加入 |
| 面板只显示 `g_6ad5…` 哈希键 | 显示「群名（123456789）」 |
| 叫错人名（只有 QQ 昵称） | `get_group_member_list` 拿**群名片** |
| 群管识别靠事件里的 role | 成员列表里直接有 `owner/admin` |
| 私聊白名单不知道填谁 | `get_friend_list` 给候选 |
| 画像里"这是谁"对不上 | 成员 → 群名片 → 画像卡 |

### 16.2 新增模块

```
lib/roster.js           🆕 拉取 + 缓存 + 查询
lib/transport/onebot.js : call(action, params) —— 统一 API 入口
storage: <store>/roster.json
```

数据结构：

```json
{
  "updatedAt": "2026-10-26T20:00:00Z",
  "self": { "uin": 100000001, "nickname": "..." },
  "groups": [ { "id": 123456789, "name": "群名", "count": 42, "max": 200 } ],
  "friends": [ { "id": 10001, "nickname": "染喵", "remark": "" } ],
  "members": {
    "123456789": {
      "updatedAt": "...",
      "list": [ { "id": 10001, "card": "群名片", "nickname": "昵称", "role": "owner|admin|member" } ]
    }
  }
}
```

### 16.3 接口（对外）

| 函数 | 作用 |
|---|---|
| `refreshGroups()` / `refreshFriends()` | 调 API 拉取并落盘 |
| `refreshMembers(groupId)` | 拉某群成员（含群名片/角色） |

| `rolesOf(groupId)` | 群主/管理员列表（替代事件缓存） |
| `rosterStats()` | 面板统计 |

### 16.4 使用点（代码里接哪）

1. **入站**：`sender.card` 优先于 `nickname`（已有字段，直接用）
2. **画像**：建像时用 `memberCard()`；画像卡显示「群名片（QQ）」

### 16.5 刷新策略（避免频繁调用）

## 13. 赛程与知识库的关系（结论：数据分开存，检索合到一起）

### 17.1 结论

**赛程不该"搬进"知识库，但应该"接进"知识库的检索。**

一句话：**结构化存储 + 知识库视图**。

| 层 | 放什么 | 为什么 |
|---|---|---|
| `matches.json`（结构化） | 日期/联赛/两队/比分/胜者/来源 | 需要**精确查询**：今天哪场、两队交手、按队名筛；还要支持"同一天同两队覆盖"、命令录入 |
| `knowledge/*.md`（文本） | 群规、术语、FAQ、链接 | 需要**模糊检索**：自然语言问"怎么闭麦" |
| 知识库的 **provider** | 把 `matches.json` 渲染成只读片段参与检索 | 让"上次那个打满五局的比赛"也能被召回 |

### 17.2 为什么不能只放知识库

如果把赛程写成 markdown 当唯一存储，会立刻丢三样东西：

1. **精确匹配**——"IG vs HLE"必须能精确命中，而不是靠中文二元词重叠（`IG` 只有两个字符，在 markdown 里几乎无法区分赛程与闲聊）
2. **确定性判断**——"今天有哪场"要能回答"有/没有"，而不是"大概相关"
3. **写入语义**——`#赛程 加` 写入时必须按 (日期, 队A, 队B) 覆盖旧记录，markdown 做不到

> 这正是我们上一轮把"从聊天猜对局"推翻的原因：**精确的东西不能靠模糊检索。**

### 17.3 为什么又要接进知识库

因为模型看到的提示词只有文本。赛程如果没有"文本形态"，就只能通过命令回应，无法参与自然对话。

所以让知识库支持 **chunk provider**：

```js
// lib/knowledge.js
const providers = [mdProvider, esportsProvider /* 🆕 */]
export async function loadChunks() {
  const out = []
  for (const p of providers) out.push(...(await p.chunks()))
  return out
}
```

`esportsProvider` 把每条赛程渲染成一个 chunk：

```
标题：2026-10-26 HLE vs IG（Worlds 2026 瑞士轮）
内容：HLE vs IG，比分待补；来源：web_search（未核）
关键词：HLE IG Worlds 瑞士轮 2026-10-26
```

好处：
- 自然提问「昨天那场谁赢了」→ 知识库能召回这条
- `#交手 IG HLE` / 话题判断仍走结构化精确查询
- **一份数据，两种用法**

### 17.4 检索优先级（避免两个来源打架）

| 问题类型 | 走哪条 |
|---|---|
| `#赛程` / `#交手` / "今天有哪场" | **结构化**（精确） |
| 自然语言"最近谁赢了""那个打满五局的" | **知识库 provider**（模糊） |
| 提示词注入 | 结构化给"今天/最近 3 条"，provider 给检索命中（去重） |

### 17.5 落地改动（小）

| 文件 | 改动 | 量 |
|---|---|---|
| `lib/knowledge.js` | 拆出 `providers` 数组，支持异步 chunk 来源 | 0.2 天 |
| `lib/esports.js` | 加 `chunks()`：把 matches 渲染成 chunk | 0.1 天 |
| 测试 | 同一份赛程：命令查得到 + 自然问句能召回 | 4 例 |
